# Handoff F4-05: API modułu zegarka do wysyłania statusu nagrania

Plik przekazania pracy między sesjami i agentami (Claude ↔ Gemini). Aktualizuj go na koniec
każdej sesji (workflow /os-handoff). Następny agent zaczyna od przeczytania tego pliku.

## Stan
- `modules/watch-connectivity/ios/WatchConnectivityManager.swift`: `sendRecordingStatus(id:status:)`
  (sygnatura zarezerwowana w F4-03, tu dopełniona) — utrzymuje `recentStatuses: [(id, status,
  updatedAt)]` (max 20, najstarsze wypadają), przy każdym wywołaniu wysyła **całą** listę przez
  `WCSession.default.updateApplicationContext(["recordingStatuses": payload])`. To świadomie
  obchodzi nadpisujący charakter `updateApplicationContext` (kontrakt zadania: "kontekst aplikacji
  WCSession nadpisuje poprzedni, nie kolejkuje") — zegarek zawsze widzi pełny, aktualny zestaw
  ostatnich statusów, nie tylko najnowszy.
- `targets/watch/QueuedRecording.swift`: nowy `RecordingStatusEntry` (id/status, `Identifiable`).
- `targets/watch/RecordingManager.swift`: `@Published recordingStatuses: [RecordingStatusEntry]`,
  nowa metoda `WCSessionDelegate`: `session(_:didReceiveApplicationContext:)` dekoduje payload i
  aktualizuje na `DispatchQueue.main` (ten sam wzorzec co istniejące `didFinish fileTransfer`).
- `targets/watch/ContentView.swift`: druga sekcja listy ("Status") pokazująca
  `recordingStatuses` z ikoną/etykietą (✓ przetworzone / ✗ błąd / zegar oczekuje), **osobna** od
  istniejącej listy kolejki transferu ("Transfer") — nagranie może już zniknąć z lokalnej kolejki
  transferu (plik dostarczony), a status przetworzenia po stronie serwera przychodzi później, więc
  scalanie tych dwóch list w jedną po id byłoby mylące.

## Kryteria akceptacji
- [x] wywołanie sendRecordingStatus z iPhone'a aktualizuje UI statusu na zegarku bez ponownego uruchamiania aplikacji zegarka — `didReceiveApplicationContext` dociera do już aktywnej sesji WCSession, `@Published` odświeża UI natychmiast; NIE zweryfikowane na prawdziwym sprzęcie (CP-DEVICE)
- [x] status kilku różnych nagrań jest widoczny jednocześnie, nie tylko ostatniego — `recentStatuses` niesie do 20 ostatnich wpisów w każdym wywołaniu, nie tylko najnowszy

## Decyzje w trakcie
- Limit 20 ostatnich statusów — arbitralna, rozsądna wartość (kontrakt nie precyzuje liczby);
  `applicationContext` ma limit rozmiaru narzucony przez system (dokumentacja Apple nie podaje
  dokładnej liczby bajtów, ale ostrzega przed dużymi payloadami), a użytkownik i tak realistycznie
  nie potrzebuje widzieć więcej niż garstki ostatnich nagrań na małym ekranie zegarka.
- Status "surowy string" (nie enum) — zgodnie z sygnaturą `sendRecordingStatus(id: String, status:
  String)` ustaloną w F4-03; `ContentView` grupuje go w 3 kategorie UI (`"done"`/`"failed"`/inne),
  a nie każdy możliwy stan z pipeline'u (`uploaded`/`transcribed`/`segmented`/...) osobno — F4-06
  (wywołujący tę metodę z prawdziwych statusów `recordings.status`) może więc przekazywać dowolny
  string z tego zbioru bez zmian w tym module.
- Lista statusów w `ContentView` celowo NIE scalona z lokalną kolejką transferu — patrz "Stan".
