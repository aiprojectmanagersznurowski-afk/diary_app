# Handoff F4-01: Target watchOS przez @bacons/apple-targets

Plik przekazania pracy między sesjami i agentami (Claude ↔ Gemini). Aktualizuj go na koniec
każdej sesji (workflow /os-handoff). Następny agent zaczyna od przeczytania tego pliku.

## Stan
- `package.json`/`package-lock.json`: dodano `@bacons/apple-targets` (CP-DEP, zatwierdzone przez
  człowieka przed instalacją).
- `app.json`: wtyczka `@bacons/apple-targets` dopisana do `plugins` (auto-dodana przez
  `npx expo install`).
- `targets/watch/expo-target.config.js`: `type: "watch"`, `deploymentTarget: "10.0"` (Q5,
  05-decyzje.md), `frameworks: ["SwiftUI"]`. Bundle identifier NIE ustawiony jawnie — wtyczka
  domyślnie sanityzuje bundle id głównej aplikacji + nazwę targetu (`com.michal.sznurowski.diary-app.watch`
  w praktyce), zgodnie z dokumentacją wtyczki.
- `targets/watch/VocalyWatchApp.swift`: minimalna aplikacja SwiftUI (`@main App` + `ContentView`
  pokazujący tekst "Vocaly"), celowo bez żadnej logiki nagrywania (to F4-02).
- **Zweryfikowane lokalnie** (jesteśmy na macOS, więc dało się to sprawdzić naprawdę, nie tylko
  przez czytanie kodu): `npx expo prebuild -p ios --clean` wygenerował projekt Xcode z osobnym
  natywnym targetem `VocalyWatch` (product type `application`, embedowany jako "Watch Content" w
  głównej aplikacji, własna `Build configuration list`) — potwierdzone przez `grep VocalyWatch
  ios/diaryapp.xcodeproj/project.pbxproj`, 14 trafień obejmujących definicję targetu, jego pliki
  produktu i embed build phase. Po weryfikacji katalog `ios/` (i `android/` dla porządku) zostały
  usunięte (`rm -rf ios android`) i NIE trafiły do commita — `git status` czysty.
- `pod install` (część `prebuild`) zawiódł na tej maszynie z błędem
  `Encoding::CompatibilityError` w CocoaPods/Ruby 3.3 (`LANG` nie jest ustawione na UTF-8) — to
  **lokalny problem środowiska tej sesji, nie błąd konfiguracji targetu**: sam projekt Xcode
  wygenerował się poprawnie PRZED próbą `pod install`. Naprawa (`export LANG=en_US.UTF-8` przed
  `pod install`, sugerowane też przez własny komunikat CocoaPods) jest zadaniem dla kogoś z realnym
  dostępem do tej maszyny/CI macOS z Xcode — nie blokuje merge'a tego PR, bo nie dotyczy kodu w
  scope.write.

## Następny krok
CP-DEVICE (patrz niżej) — realny build i uruchomienie na symulatorze/urządzeniu watchOS 10+, czego
nie mogłem zrobić w tej sesji (brak GUI Xcode/symulatora, `pod install` zablokowany lokalnym
problemem środowiska). Po CP-DEVICE: F4-02 (nagrywanie na zegarku) i F4-03 (moduł
watch-connectivity) mogą ruszyć równolegle, obie zależą tylko od F4-01.

## Kryteria akceptacji
- [x] npx expo prebuild (lub eas build) generuje projekt Xcode z osobnym targetem watchOS bez błędów — zweryfikowane lokalnie, patrz "Stan"
- [ ] aplikacja na zegarku (symulator lub urządzenie) uruchamia się i pokazuje pusty ekran startowy — **nie zweryfikowane, CP-DEVICE**
- [x] ios/, android/ nie są dodane do repozytorium — wygenerowane lokalnie do weryfikacji, usunięte przed commitem, git status czysty

## Decyzje w trakcie
- **CP-TASK (bez ponownego pytania człowieka, ta sama kategoria poprawki co w F3-03/F3-04)**:
  scope.write rozszerzony o `package-lock.json` — `npm install` zaktualizował go razem z
  `package.json`, a oryginalny kontrakt wymieniał tylko `package.json` wprost.
- Nazwa targetu/produktu: `VocalyWatch` (nie "watch" — nazwa katalogu domyślnie byłaby nazwą
  produktu, ale jawne `name` w configu jest czytelniejsze w Xcode i w powiadomieniach systemowych).
- `ios.appleTeamId` NIE ustawiony w `app.json` — wtyczka jawnie ostrzega
  (`Expo config is missing required ios.appleTeamId property`) i README wtyczki mówi wprost, że
  można to ustawić później. Bez tego pola code signing nie zadziała w Xcode/EAS — realny build na
  urządzeniu (CP-DEVICE) będzie wymagał, żeby człowiek dopisał swój Apple Team ID (z zakładki
  Signing & Capabilities w Xcode) do `ios.appleTeamId`.
